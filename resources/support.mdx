Brian2 has an active support ecosystem built around a community forum, a public bug tracker, and thorough documentation. Whether you are encountering unexpected simulation results, a runtime error, or a conceptual question about neural modelling, the channels below are the fastest route to a solution. Before posting, it is always worth searching the existing threads — many common problems have already been answered in detail.

## Community Forum and GitHub Issues

The primary support channel for Brian2 is the Discourse community forum at [brian.discourse.group](http://brian.discourse.group). This is the right place for usage questions, modelling advice, and general discussion. For confirmed software bugs, open an issue directly on the GitHub repository.

## Finding Your Brian2 Version

When reporting a problem, always include the exact version of Brian2 you are running. Different installation methods expose different commands to retrieve this information.

<Tabs>
  <Tab title="Python (universal)">
    The most reliable method works regardless of how Brian2 was installed and ensures you are querying the environment that actually runs your scripts:

    ```python
    import brian2
    print(brian2.__version__)
    # e.g. 2.4.2
    ```

    If you suspect a version mismatch between environments, check the installation path as well:

    ```python
    import brian2
    print(brian2.__file__)
    # e.g. /home/user/anaconda3/envs/brian2_test/lib/python3.9/site-packages/brian2/__init__.py
    ```

    The path reveals exactly which conda environment or Python installation is being used — helpful when you think you have updated Brian2 but the old version is still being loaded.
  </Tab>
  <Tab title="conda">
    If you installed Brian2 with conda, use:

    ```bash
    conda list brian2
    ```
  </Tab>
  <Tab title="pip">
    If you installed Brian2 with pip, use:

    ```bash
    pip show brian2
    ```
  </Tab>
</Tabs>

<Note>
  If you installed a development version of Brian2, the version string carries additional information about the number of commits beyond the last release:

  ```python
  import brian2
  print(brian2.__version__)
  # e.g. 2.4.2.post408
  # This means 408 commits were added after the 2.4.2 release.
  ```
</Note>

## How to Ask Effective Questions

The quality of the response you receive is directly proportional to the quality of the question you ask. Following these steps will get you the fastest and most accurate answer.

<Steps>
  <Step title="Try to solve it yourself first">
    Read the documentation thoroughly, including the search feature, the index, and the reference documentation. Many questions are answered there.
  </Step>
  <Step title="Search existing threads">
    Search the forum archives and the GitHub issue tracker. The same problem may have already been answered.
  </Step>
  <Step title="Create a minimal reproducible example">
    Before writing to the forum, reduce your code to the smallest possible script that still reproduces the problem. You will get the fastest response if you can share just a handful of lines that clearly demonstrate what is not working.

    A good minimal example:
    - Imports only what is needed
    - Uses hardcoded values rather than loading external files
    - Reproduces the problem every time it is run
    - Is short enough to read in under a minute
  </Step>
  <Step title="Include your Brian2 version">
    Always report the exact version string (see above), your operating system, and your Python version. For code generation issues, also mention whether you are using runtime mode or C++ standalone mode.
  </Step>
</Steps>

## Known Issues Overview

In addition to the common problems listed below, you can always browse the full list of open bugs on the [GitHub issue tracker](https://github.com/brian-team/brian2/issues?q=is%3Aopen+is%3Aissue+label%3Abug).

<AccordionGroup>
  <Accordion title="Problems with numerical integration">
    In some cases the automatic choice of numerical integration method is not appropriate because of parameter choices that cannot be determined in advance. This typically produces `nan` (not a number) values in the results, or large oscillations. Brian2 will generate a warning to alert you, but will not raise an error. Specify the integration method explicitly in your `NeuronGroup` to resolve this.
  </Accordion>
  <Accordion title="Parallel simulations with C++ standalone">
    Simulations using the C++ standalone device store results in a dedicated directory (`output` by default). Running multiple simulations in parallel against the same directory causes compilation errors or incorrect results. Either pass a unique `directory` argument to `.set_device()` or `.build()`, or use `directory=None` to let Brian2 create a unique temporary directory automatically. The chosen path is accessible after the run via `device.project_dir`.
  </Accordion>
  <Accordion title="Parallel Cython simulations on NFS (computing clusters)">
    Generated Cython code is cached on disk and reused across runs. On machines using NFS (common on computing clusters), the file-locking mechanism Brian2 uses to prevent concurrent writes is very slow. Use a per-process cache directory and disable the lock:

    ```python
    from brian2 import *
    import os
    cache_dir = os.path.expanduser(f'~/.cython/brian-pid-{os.getpid()}')
    prefs.codegen.runtime.cython.cache_dir = cache_dir
    prefs.codegen.runtime.cython.multiprocess_safe = False
    ```
  </Accordion>
  <Accordion title="Jupyter notebooks and C++ standalone progress reporting">
    When running C++ standalone simulations with `report='text'`, progress output does not appear inside the notebook. If you started the notebook from a terminal, the output will appear there instead. This is a limitation of how Jupyter handles subprocess output.
  </Accordion>
  <Accordion title="Slow C++ standalone on recent Ubuntu">
    Some versions of the GNU standard library used by recent Ubuntu releases have a bug that dramatically slows down standalone simulations on modern hardware. Brian2 sets the `LD_BIND_NOW` environment variable automatically as a workaround. If this causes problems, adjust the `prefs.devices.cpp_standalone.run_environment_variables` preference.
  </Accordion>
  <Accordion title="Windows: CMD windows opening with Spyder 3 IDE">
    CMD windows appearing when running Brian2 in Spyder 3 are caused by interaction with the integrated IPython terminal. Either change the run configuration to "Execute in an external system terminal", or apply the patch described in [GitHub issue #1140](https://github.com/brian-team/brian2/issues/1140).
  </Accordion>
</AccordionGroup>

## Logging and Debugging

Brian2 includes a built-in logging system that writes warnings and diagnostic information to both the console and a log file. Understanding log levels and knowing how to adjust them is essential for debugging simulations that behave unexpectedly.

### Log Levels

Each log message in Brian2 has one of the following severity levels:

| Level        | When it appears                                                                 |
|--------------|---------------------------------------------------------------------------------|
| `ERROR`      | Only when an exception is raised and the operation is interrupted               |
| `WARNING`    | When Brian2 suspects a likely bug, but cannot be certain                        |
| `INFO`       | When Brian2 makes an automatic choice on the user's behalf                      |
| `DEBUG`      | Additional detail useful when a simulation is not working as expected           |
| `DIAGNOSTIC` | Detailed internals useful when tracking down bugs in Brian2 itself              |

By default, messages at `INFO` level and above are printed to the console, while messages at `DEBUG` level and above are written to the log file. The log file is deleted automatically after a successful run. To retain it, set:

```python
prefs.logging.delete_log_on_exit = False
```

<Note>
  Most logging preferences are applied during Brian2's initialisation, which happens at import time. Setting `prefs.logging.file_log = False` in your script after importing will not take effect. To ensure logging preferences are respected, call `BrianLogger.initialize()` after setting them, or place the preferences in a Brian2 preferences file.
</Note>

### Adjusting Log Levels with BrianLogger

Use the `BrianLogger` class to control what appears on the console:

```python
from brian2 import *

# Show debug messages on the console
BrianLogger.log_level_debug()

# Suppress code generation messages on the console
BrianLogger.suppress_hierarchy('brian2.codegen')

# Suppress preference messages even in the log file
BrianLogger.suppress_hierarchy('brian2.core.preferences', filter_log_file=True)

# Suppress a specific message by name
BrianLogger.suppress_name('resolution_conflict')
```

<Warning>
  `suppress_hierarchy` and `suppress_name` suppress messages regardless of their level, including `WARNING` and `ERROR`. Use them with care to avoid hiding important information.
</Warning>

### Logging to a File

By default, Brian2 writes a log file with `DEBUG`-level detail. You can increase verbosity to `DIAGNOSTIC` for code-generation debugging, or turn file logging off entirely:

```python
from brian2 import *

# Log everything including internal code generation details
prefs.logging.file_log_level = 'DIAGNOSTIC'

# Disable file logging entirely
prefs.logging.file_log = False

# Then reinitialise to apply changes made after import
BrianLogger.initialize()
```

### Logging and Multiprocessing

Brian2's logging system is not designed for multiple parallel processes started via Python's `multiprocessing` module. Console messages from different processes are interleaved with no indication of which process they came from. To avoid cluttered output, restrict logging to errors only before spawning subprocesses:

```python
BrianLogger.log_level_error()
```

File logging is automatically disabled for sub-processes to avoid write conflicts. If you need per-process log files, call `BrianLogger.initialize()` inside each sub-process so that each one writes to its own file.
